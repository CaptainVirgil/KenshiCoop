## Reports and status

### 1. FPS 30–45 in a city — **NOT the plugin**

`[budget]` settles it: the plugin spends ~0.33 ms per frame and **zero frames
exceeded 2 ms**. At 30 fps a frame is 33 ms, so the plugin is ~1% of it. During
the sampled window the client was running ~80 fps (401 frames per 5 s).

Maxed settings + a Kenshi city is the explanation. Kenshi is famously
single-thread-bound in towns. **Not worth optimising the plugin for this.**

### 2. Bed desync — **root-caused, and it is known debt**

> "he put me in a bed but it shows me on the floor on my screen (name tag does
> show above the bed); for him it shows me in the bed. Reloading fixed it."

Log:

```
[furn] RECV ENTER id=36 occ=1,1709716736 furn=3001,3781250048 kind=1 ok=1
[furn] BED FAST-EXIT occ=1,1709716736 ok=1 hostMoving=1
```

The peer's ENTER lands, then **BED FAST-EXIT immediately takes the body back
out** because the incoming stream still reads `hostMoving=1`. The owner's copy
stays in bed, ours does not — exactly the "actions appear inverted" class.

This is **pre-existing debt the sync-review skill already names**: the bed
fast-exit is the one heal that does NOT go through `healDue()`. It gates on
`furnEnterHoldMs`, an absolute wall-clock deadline stamped once, with no
stream-progress term — so it can fire against a sample that predates the ENTER
it is reacting to. At 78 ms RTT that window is far wider than on loopback, which
is why this never showed up locally.

**Fix direction:** route the fast-exit through `healDue()` like every other
heal, so it requires the stream to have actually ADVANCED (not merely for wall
time to have passed) before it overrides a reliable ENTER event.

**FIXED.** `Driven` now carries `furnEnterSample` alongside `furnEnterHoldMs`:
the ENTER stamps `interp.newestMs()` as well as the deadline, and the fast-exit
needs BOTH past before it may fire — the same two-term test `healDue()` applies,
written inline because the hold is armed by an event rather than by a sighting.
This is the debt the sync-review skill named; it is now paid, and that skill's
"one known exception" paragraph is stale.

### 3. Doors looping open/closed — **confirmed, no sync traffic at all**

`doorSync` is ON in the effective config, but the join log contains **zero
`[door]` lines** across the whole session. So the channel is enabled and silent:
both engines are opening the door for their own characters and neither is
describing it to the other. That is precisely the "one writer per thing"
violation the doctrine says doors already committed once.

Under investigation — see below.

### 4. Rain not synced — **no weather traffic on the join**

**Zero `[weather]` lines** in the join log. The host publishes and the join
applies, so the host's log is the one that decides between:

- host never SENT (publish gate, or read failed there), or
- join received but `applyWeather` returned false (stringID did not resolve in
  the receiver's own season table — deliberately dropped rather than guessed)

**Need the brother's log to tell these apart.** This is the one diagnostic gap
noted when the channel shipped: both cases are currently silent on the receiver.

**HOST LOG SETTLES HALF OF IT.** The host published — four `[weather] SEND`,
all `'48711-rebirth.mod' str=1.00 eff=1.00 season=0`. So the join received and
dropped, or never received. Player report the same night: **rain on the join,
none on the host, in the same spot** — the join kept its own roll rather than
adopting the host's, which is what a drop looks like.

`rebirth.mod` is base-game data present on both installs (`data/rebirth.mod`),
so a missing-mod stringID mismatch is *not* the likely cause. Cause still
unknown — and that is the actual defect.

**FIXED (the diagnosis, not yet the cause).** `applyWeather` had four distinct
`return false` exits that were indistinguishable at the call site, and the
caller logged only the success edge. It now reports which exit it took
(`no-weather-system` / `no-active-region` / `sid-not-in-our-table` /
`field-write-faulted` / `already-matching`) and the receiver logs every outcome,
rate-limited to one line per distinct reason. Next session's join log names the
cause directly. Note also that the host's `[engine] CAPS` line has **no
`weather=` or `dialogue=` entry** — `[caps] 0 of 17` never covered these two
channels, so a failed resolve here could never have raised a `[caps] WARNING`;
`no-weather-system` now covers that case explicitly.

### 6. NPC moonwalk STILL happening — **my earlier fix was half a fix**

Same symptom as the 2026-08-09 recording. The live log shows exactly why:

```
haltDrv=10401                    <- the freeze exemption firing 10,401 times
worstZero zero=337 active=346    <- and bodies STILL 97% frozen
[census] FREEZE  1412
[census] park    1006
```

The exemption is working — ten thousand freeze-vs-drive collisions caught — and
the bodies are frozen anyway, because **the freeze was not the only thing
halting them**. `parkDivergedCopy` does a halt+teleport, and it is called from
THREE places: the near pass, the wide pass, and `reconcileProxy`. Only the last
was guarded. 1,006 parks this session went through the two that were not.

**Fixed** by moving the guard INSIDE `parkDivergedCopy` rather than at a call
site, so a fourth caller cannot reintroduce it. Same lesson as the wire-string
termination one already in `CLAUDE.md`: do the safety thing where everything
funnels, not at each call site.

Needs a rebuild to take effect — not yet in the running build.

### 7. Doors loop AT NIGHT, NPCs "spamming" them — **the root cause of several symptoms**

Player note: the door loop only happens at night, and it looks like the NPCs are
doing it.

That is exactly right, and the log says why:

```
[ai] suspended=23   driven=123      <- only ~25 of 123 driven bodies are quieted
mid-rest releases:  2932
parks:              5161
```

**~98 driven bodies are running their own local AI while the peer's stream is
also writing them.** Two writers on one body, a hundred times over.

The mechanism is the mid-rest release (`ReplicatorDrive.cpp`, "movers stay
driven"): when a mid-band body stops moving it is erased from `drivenChars_`
AND deliberately skips the AI suspend, on the stated theory that local AI will
"idle the body naturally between host movements". **Local AI does not idle** -
it runs the NPC's schedule. At night that schedule is *go home and sleep*, which
means pathing through doors. So ~98 locally-AI'd copies operate doors that the
host's copies are also operating, and with the door channel silent nothing
reconciles the two.

Same root feeds the moonwalk: those bodies are then park-teleported (5,161
times) and halted while the drive tries to walk them.

**This is the "absence is not evidence" family again.** Releasing to local AI
assumes local AI will do nothing; it does plenty. The stationary keepalive
shipped in v0.50 was meant to close exactly this - it puts a still body's pose
on the wire so the peer can HOLD it - but the release still fires, because it
gates on `!npcMoving` rather than on whether a fresh sample exists.

**Fix direction:** when a mid body is at rest and a fresh keepalive is in hand,
do not release it to local AI at all - keep it suspended and hold it where the
owner says it is. The keepalive already provides the authority to do that.

**FIXED.** The mid-rest release now checks for a fresh word from the owner
(`MID_STILL_HOLD_MS = 5000`, against the 1500 ms keepalive cadence — three
missed keepalives before we let go). With one in hand the body stays in
`drivenChars_`, keeps its AI suspended and holds the owner's pose; only a body
the owner has genuinely stopped describing is handed back to local AI. That
removes the second writer from ~98 bodies, which is the same root as the
moonwalk and the night door-flapping.

### 8. No hit markers — **and the damage may not be landing either**

```
role=HOST                                 <- coop_config.json on the JOIN's machine
[role] panel role is JOIN; log renamed    <- what is actually being played
handshake: peer present id=0 (local id=1) <- confirmed join
[dmg] ... damage guard ON (host, ...)     <- but the damage code took the HOST branch
```

`reportCombat_` is set from `g_cfg.isHost` at plugin load, **before the panel
role exists**. Playing JOIN with a config that says `host` therefore leaves
combat reporting OFF.

Two consequences, the second far worse than the first:

1. No damage floaters - the new floater code lives inside the report block.
2. **Melee on the host's NPCs may do nothing at all.** The guard still suppresses
   the local swing (that part is role-independent), but with reporting off
   nothing is sent for the host to apply. Suppressed locally, never reported
   remotely. `0` combat hits were published this session.

**Workaround, no rebuild:** set `"role": "join"` in `coop_config.json` and
restart, so the configured role matches the played one.

**Real fix:** anything derived from `isHost` must be re-evaluated when the panel
role changes, not frozen at load. The log filename already does this (it renames
itself); the behaviour flags do not.

**FIXED.** `coopUiConnect` now re-derives every role-dependent flag from the
role actually being played — `g_cfg.isHost`, combat reporting on both the
replicator and the engine facade, gate authority, and NPC streaming — and logs
`[role] behaviour re-derived for ...`. The config file no longer has to agree
with the button you pressed. The workaround above is no longer needed.

### 9. Crash talking to a seated NPC — `0xC0000005` at address `0x0`

A null dereference, and a different exception from the `0xE06D7363` fixed
earlier in the session. The crash dump's module list came back empty, so this is
reasoned from the code rather than from a resolved frame.

The dialogue hooks are the newest code on that exact path and they broke the
rule the rest of the engine facade follows: **51 `__try` blocks in
`EngineWorld.cpp`, and zero of them in the two functions that read an
engine-supplied `std::string` across the MSVCP100 boundary.** They also called
their trampolines unconditionally — and a call through a null function pointer
is precisely an access violation at address `0`.

Hardened three ways: the capture body moved into its own function so the hooks
can be wrapped in SEH without tripping C2712 (`std::string` requires unwinding),
both trampolines are null-checked before the call through, and a half-installed
hook pair now says so (`[dlg] WARNING hook install incomplete`) instead of
producing a channel that captures nothing for no stated reason. `showDialogue`'s
`floaterSpawn` is under SEH too — the body it attaches to was enumerated
microseconds earlier and zone streaming can retire one in between.

**Not confirmed fixed** — no resolved frame ties the crash to this code. It is
the strongest candidate on the path, and the hardening is correct regardless.

### 10. The host hangs — and it is a HANG, not a crash

The second session's host log ends mid-play. It was nearly read as a crash. It
is not:

```
19:31:22.413  [med] SEND ...              <- last main-thread line
19:31:28.845  [net] bandwidth out=0.7 in=3.7   (window 7s)
...
19:31:50.845  [net] bandwidth out=0.3 in=3.9   <- last line, 28s later
```

`[net] bandwidth` is emitted by the **ENet thread**. Every main-thread line
stopped at 19:31:22 while the network thread ran on for 28 seconds. `out`
collapsed 5.4 -> 0.3 KB/s (nothing publishing) while `in` held near 5 KB/s
(nothing draining the inbound queue). `[budget] frames=431 over2ms=0` right
before: no degradation, then an instantaneous stop. That is a spin or a block.

The earlier crash (v0.51, `.prev`) is a DIFFERENT failure - main-thread lines
run right to the last line, no net-only tail. Two distinct bugs, and the log
could not tell them apart.

**Shipped: a main-thread watchdog.** The main thread stamps a heartbeat and a
phase label (`publish` / `engine` / `apply` / `frame-end`); the net thread's
existing 5 s tick reports any gap over 5 s as
`[watchdog] MAIN THREAD STALLED <ms> phase='<x>' beats=<n>`, re-stamping every
15 s so the final line bounds the freeze, and logging `RECOVERED` if it
unfreezes. `phase='engine'` means Kenshi hung with us on the stack;
`phase='publish'` or `'apply'` means we did. The asymmetry between the two
threads is the whole tool: the net thread is the only witness a frozen main
thread has.

**Both crashes sit near machines and seats.** v0.51: `[taskkey] key=221
desc='Operating machine'` + two `[seatres]` lines, and a `[budget]` spike of
`max=20864us` - 20.8 ms against a 77 us average. v0.52: a production machine
seen for the first time (`[prod] ... first=1`) and its inventory enumerated.
The earlier session's report was "crashed talking to an npc in a chair". Not
yet a diagnosis - task 221 resolved cleanly many times in the role-swap session
that followed - but three sightings in one subsystem is worth the next look.

### 11. Damage floaters are invisible to the HOST, and the cause is not the last one

Reported again while hosting, having been reported while joining. Same symptom,
two different bugs - the role fix in v0.51 closed only the join's.

The floater lives inside the report gate:

```cpp
if (g_combatReport && !g_reportAttackers.empty() && ...) {
    rd.flesh += ...;                              // accumulate to report
    if (g_dmgFloaters) floaterSpawn(self, n, 1);  // nested INSIDE
}
return HIT_MISSED;                                // suppressed regardless
```

`g_combatReport` is `!isHost`. So a host suppresses the swing and neither draws
the number nor accumulates anything to send.

**Moving the floater out would be a lie.** Tracing it: every DRIVEN body is
damage-guarded, and on the host the driven bodies are the peer's characters. A
host swing at one is suppressed AND unreported, so it lands nowhere. A floater
there would report damage that never happens.

The real fix is symmetric: whoever suppresses must report. `applyCombatHits` is
not role-gated and would accept it - **except** it does `SKIP (own body)`, which
blocks precisely the host->join direction. Two-part change, real desync risk,
deliberately not taken mid-session.
