## Reports and status

### 1. FPS 30–45 in a city — **NOT the plugin**

`[budget]` settles it: the plugin spends ~0.33 ms per frame and **zero frames
exceeded 2 ms**. At 30 fps a frame is 33 ms, so the plugin is ~1% of it. During
the sampled window the client was running ~80 fps (401 frames per 5 s).

Maxed settings + a Kenshi city is the explanation. Kenshi is famously
single-thread-bound in towns. **Not worth optimising the plugin for this.**

### 2. Bed desync — **root-caused, and it is known debt**

> "he put me in a bed but it shows me on the floor on my screen (name tag does
> show above the bed); for him it shows me in the bed. Reloading fixed it."

Log:

```
[furn] RECV ENTER id=36 occ=1,1709716736 furn=3001,3781250048 kind=1 ok=1
[furn] BED FAST-EXIT occ=1,1709716736 ok=1 hostMoving=1
```

The peer's ENTER lands, then **BED FAST-EXIT immediately takes the body back
out** because the incoming stream still reads `hostMoving=1`. The owner's copy
stays in bed, ours does not — exactly the "actions appear inverted" class.

This is **pre-existing debt the sync-review skill already names**: the bed
fast-exit is the one heal that does NOT go through `healDue()`. It gates on
`furnEnterHoldMs`, an absolute wall-clock deadline stamped once, with no
stream-progress term — so it can fire against a sample that predates the ENTER
it is reacting to. At 78 ms RTT that window is far wider than on loopback, which
is why this never showed up locally.

**Fix direction:** route the fast-exit through `healDue()` like every other
heal, so it requires the stream to have actually ADVANCED (not merely for wall
time to have passed) before it overrides a reliable ENTER event.

### 3. Doors looping open/closed — **confirmed, no sync traffic at all**

`doorSync` is ON in the effective config, but the join log contains **zero
`[door]` lines** across the whole session. So the channel is enabled and silent:
both engines are opening the door for their own characters and neither is
describing it to the other. That is precisely the "one writer per thing"
violation the doctrine says doors already committed once.

Under investigation — see below.

### 4. Rain not synced — **no weather traffic on the join**

**Zero `[weather]` lines** in the join log. The host publishes and the join
applies, so the host's log is the one that decides between:

- host never SENT (publish gate, or read failed there), or
- join received but `applyWeather` returned false (stringID did not resolve in
  the receiver's own season table — deliberately dropped rather than guessed)

**Need the brother's log to tell these apart.** This is the one diagnostic gap
noted when the channel shipped: both cases are currently silent on the receiver.

### 5. Dialogue — **working**

13 `[dlg]` lines captured. The hooks fire on a real session.

### 6. NPC moonwalk STILL happening — **my earlier fix was half a fix**

Same symptom as the 2026-08-09 recording. The live log shows exactly why:

```
haltDrv=10401                    <- the freeze exemption firing 10,401 times
worstZero zero=337 active=346    <- and bodies STILL 97% frozen
[census] FREEZE  1412
[census] park    1006
```

The exemption is working — ten thousand freeze-vs-drive collisions caught — and
the bodies are frozen anyway, because **the freeze was not the only thing
halting them**. `parkDivergedCopy` does a halt+teleport, and it is called from
THREE places: the near pass, the wide pass, and `reconcileProxy`. Only the last
was guarded. 1,006 parks this session went through the two that were not.

**Fixed** by moving the guard INSIDE `parkDivergedCopy` rather than at a call
site, so a fourth caller cannot reintroduce it. Same lesson as the wire-string
termination one already in `CLAUDE.md`: do the safety thing where everything
funnels, not at each call site.

Needs a rebuild to take effect — not yet in the running build.
